REVIEW-004 + REVIEW-010: анализ и регрессионные тесты, этап 1

Ниже сохранены результаты первого этапа для commit `ca19a2f`, до согласования
архитектурного решения. Результаты реализации второго этапа приведены в конце.
На первом этапе production-код, миграции и конфигурация не изменялись.
Добавленные отрицательные тесты намеренно падают: они фиксируют рекомендуемое
безопасное поведение для согласования перед реализацией.

Фактически разрешённые переходы через HTTP (при корректном payload и владении записью):

| Операция | Исходное состояние | Разрешённое новое состояние | Что происходит со второй записью |
| --- | --- | --- | --- |
| PATCH ScheduledTraining | planned | planned, completed, cancelled | TrainingPlan не меняется |
| PATCH ScheduledTraining | completed | planned, completed, cancelled | TrainingPlan не меняется |
| PATCH ScheduledTraining | cancelled | planned, completed, cancelled | TrainingPlan не меняется |
| PATCH TrainingPlan | draft или approved | draft, approved | ScheduledTraining не меняется |
| PATCH TrainingPlan | generating или failed | draft, approved | ScheduledTraining не меняется |
| PATCH TrainingPlan | completed | completed, с заменой содержимого | ScheduledTraining не меняется |
| POST TrainingPlan/complete | любое из пяти состояний плана | completed | Любой статус ScheduledTraining заменяется на completed |
| POST TrainingPlan | плана ещё нет | draft, approved | Статус ScheduledTraining не проверяется и не меняется |

Дополнительно: генератор AI сохраняет `draft`, проверяя отсутствие плана, но не
статус тренировки. `generating` и `failed` объявлены в модели и PostgreSQL CHECK;
в текущем генераторе переходов к этим состояниям нет. Policies проверяют владельца,
а не допустимость перехода. FormRequest выбирает статусы по route-bound модели до
транзакции. PostgreSQL CHECK проверяют значения отдельных строк, не сочетание
статусов связанных записей.

Оценка сочетаний до появления TrainingSession:

| ScheduledTraining | TrainingPlan отсутствует | draft / approved | completed | generating / failed |
| --- | --- | --- | --- | --- |
| planned | допустимо | допустимо | противоречие | техническое состояние подготовки |
| cancelled | допустимо | сохранённая подготовка отменённой тренировки | противоречие | сохранённое техническое состояние |
| completed | допустимо: тренировка без плана | противоречие | согласовано | противоречие |

При наличии плана временный инвариант: `TrainingPlan.completed` тогда и только
тогда, когда `ScheduledTraining.completed`. Это совместимость текущей модели,
а не утверждение, что документ плана должен навсегда хранить фактические результаты.

Подтверждения сценариев A–E:

| Сценарий | Фактический результат | Оценка |
| --- | --- | --- |
| A: завершение, затем PATCH scheduled → planned | HTTP 302, пара planned / completed | Дефект; аналогично разрешён cancelled / completed |
| B: отмена, затем завершение плана | HTTP 302, отмена заменяется парой completed / completed | Нет проверки перехода из cancelled |
| C: GET edit, отдельное завершение, затем новый PATCH со старым draft | HTTP 422, данные сохранены | Этот последовательный сценарий уже защищён |
| C/D: PATCH прошёл валидацию, другой запрос завершил план, PATCH продолжил сохранение | Блоки и упражнения заменены; draft→draft оставляет статус completed, approved→draft возвращает draft, draft→approved возвращает approved | Подтверждённая гонка; CompletedTraining остаётся completed во всех трёх случаях |
| D: валидация отмены, завершение плана, сохранение отмены | Пара cancelled / completed | Блокировка ScheduledTraining сама по себе не проверяет переход |
| D: завершение загрузило route model, другой запрос отменил тренировку | Отмена перезаписана завершением | Нет повторной проверки состояния ScheduledTraining |
| D: два перекрывающихся завершения | Оба успешны, статусы completed / completed, блоки не заменяются | Противоречия статусов не воспроизведено |
| E: повторное завершение через пять минут | Статусы и история сохранены; updated_at тренировки изменён | Идемпотентность статусов есть; строгого no-op нет |

Отдельно подтверждены: завершение `generating`/`failed`; замена содержимого уже
завершённого плана с `status=completed`; создание нового `draft` для тренировки,
уже помеченной `completed`. Это пути обхода того же инварианта, а не другие замечания аудита.

Причина REVIEW-004: SaveTrainingPlan::update использует старый объект, не загружает
свежий план под блокировкой и безусловно удаляет/создаёт его вложенные записи.
Eloquent записывает dirty-поля относительно старого объекта: неизменный draft не
обязательно перезапишет новый completed, но изменение draft↔approved перезапишет.
Поэтому одной защиты поля status недостаточно — нужна проверка перед replaceBlocks.

Причина REVIEW-010: существуют два независимых входа изменения статуса;
CompleteTrainingPlanAction синхронизирует обе записи, но не проверяет исходные
состояния, а ScheduledTraining PATCH вообще не синхронизирует и не проверяет план.

Предлагаемая минимальная модель, ещё не реализованная:

| Исходная пара ScheduledTraining / TrainingPlan | Операция | Результат |
| --- | --- | --- |
| planned / draft или approved | Редактирование плана | draft ↔ approved, содержимое редактируется |
| planned / draft или approved | Отмена | cancelled / прежний план, содержимое сохранено |
| cancelled / draft или approved | Явное возвращение в расписание | planned / прежний план |
| cancelled / draft или approved | Редактирование плана | Подготовку можно сохранить, отмена остаётся |
| planned / draft или approved | POST complete | Атомарно completed / completed; обязательное утверждение не добавляется |
| cancelled / любой незавершённый план | POST complete | Ошибка валидации; сначала требуется явное возвращение в planned |
| planned / generating или failed | POST complete | Ошибка валидации |
| completed / completed | POST complete | Успех без записи в БД и изменения timestamps |
| completed / completed | PATCH статуса scheduled в planned/cancelled | Ошибка валидации; оба статуса сохраняются |
| completed / completed | PATCH содержимого плана | Ошибка валидации; завершённый план — неизменяемый снимок |
| любая тренировка с незавершённым планом | PATCH scheduled → completed | Ошибка валидации; используется существующий endpoint complete |
| completed / плана нет | Создание нового ручного/AI плана | Ошибка валидации; нельзя создавать историю подготовки задним числом |

Статусы тренировок без плана остаются с прежними правилами. Другие поля тренировки
и TrainingNote редактируются по прежним правилам. Подготовку для cancelled можно
сохранять; создание черновиков для planned/cancelled сохраняется. Возврат
generating/failed к draft/approved через существующий ручной PATCH не запрещается
этим предложением: отдельный жизненный цикл AI сейчас не вводится.

Все решения принимаются внутри существующих транзакций по свежим записям.
Единый порядок `FOR UPDATE`: сначала ScheduledTraining, затем связанный TrainingPlan.
Это касается complete, save/update и PATCH статуса тренировки; create и финальная
запись AI уже блокируют ScheduledTraining. После получения блокировок повторно
проверяется допустимость операции, до изменений полей и удаления блоков.
FormRequest остаётся первичной проверкой payload, Policies — проверкой владельца.
Ожидаемые отказы оформляются ValidationException: JSON получает 422 с именем поля,
обычная форма — redirect с validation errors. Новые сервисы, интерфейсы, state
machine, версии строк и триггеры для этой задачи не нужны.

TrainingSession в будущем должен хранить факт проведения и результаты отдельно
от плана подготовки. Пока `completed` плана сохраняется как терминальная отметка
существующей модели. Изменение завершённых упражнений заменяется отдельной
будущей семантикой исправления фактических результатов; TrainingSession и её
таблицы сейчас не реализуются. Несогласованные старые пары не исправляются
автоматически и не считаются идемпотентным повтором завершения: для их исправления
нужно отдельно определить, какое состояние отражает действительную историю.

Этап 2: реализация согласованной модели

SaveTrainingPlan::update теперь сначала блокирует свежую ScheduledTraining,
затем свежий TrainingPlan. Завершённое занятие или план отклоняют изменение до
update и replaceBlocks. Устаревшие статусы не используются для сохранения.
Создание ручного плана проверяет свежий статус и наличие уже созданного плана
под блокировкой; обычный конкурентный конфликт возвращает validation error,
а не нарушение UNIQUE в PostgreSQL.

CompleteTrainingPlanAction использует тот же порядок блокировок. Только planned
с draft/approved переходит атомарно в completed/completed. Согласованная пара
completed/completed возвращается без UPDATE и событий моделей. Cancelled,
generating/failed и старые несогласованные пары отклоняются без изменений.

ScheduledTraining PATCH использует прежний validatedForUpdate: сохраняются
только явно отправленные поля, а пропуски проверяются по свежей модели. Связанный
план блокируется после занятия. Проверяются как исходная согласованность пары,
так и следующий статус. В отличие от первоначального предложения, утверждённое
правило запрещает обычный возврат completed → planned/cancelled также для
занятия без плана. Административное завершение занятия без плана остаётся
доступным; упражнения и фактические результаты при этом не создаются.

AI читает актуальное занятие перед запросом, а после ответа LLM повторно
проверяет completed под блокировкой перед сохранением. SQL-транзакция не
охватывает вызов LLM. Весь существующий AI-контекст во время ожидания ответа
не проверяется заново: это отдельный REVIEW-003 и в эти изменения не входит.

UI скрывает редактирование завершённого плана и неподходящее завершение,
не предлагает completed занятия при создании плана, отображает validation
errors и предупреждение для старой противоречивой пары. GET edit завершённого
плана перенаправляется на просмотр. TrainingNote сохраняет прежние правила.
В одном тесте REVIEW-002 исправлена только фикстура completed-плана: статус
его занятия также completed. Старые противоречивые пары тестируются отдельно.
