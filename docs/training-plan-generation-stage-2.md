# AI-генерация: REVIEW-003/006, этап 2

Используются существующие AI-клиенты, построитель контекста и валидатор.
Синхронный endpoint закрыт с HTTP 410; интерфейс использует отдельную операцию
генерации и polling каждые две секунды. Очередь — Laravel database на PostgreSQL.
Новых зависимостей, Redis, RAG и TrainingSession нет.

## Жизненный цикл и состояния

1. POST с UUID `request_key` блокирует актуальное занятие и существующий план,
   проверяет доступность, вычисляет fingerprint и резервирует операцию.
   Generation и сериализованная Job записываются в одной транзакции одного
   PostgreSQL-соединения через `beforeCommit()`. Rollback удаляет обе записи;
   сбой HTTP после commit не теряет Job.
2. Worker в короткой транзакции получает `run_token` и lease, проверяет актуальные
   записи и fingerprint. Повторная доставка при действующем lease освобождает
   Job с задержкой, а не подтверждает её без продолжения обработки.
3. Ещё одна проверка непосредственно перед отправкой фиксирует
   `request_started_at`. Внешний LLM-вызов выполняется без SQL-транзакции.
4. Ответ проходит прежний валидатор и сохраняется как зашифрованный,
   нормализованный JSON для восстановления. Сохраняется только содержимое плана,
   без исходного prompt и неиспользуемых полей ответа провайдера.
5. Публикация вновь проверяет token, lease, fingerprint, отсутствие плана,
   состояние занятия и активность цели. План, блоки, упражнения и `succeeded`
   сохраняются атомарно. Временный ответ удаляется.

| Состояние | Поведение |
|---|---|
| `queued` | Ожидание Job или безопасного повтора до `next_attempt_at` |
| `running` | Обработка с ограниченным lease и уникальным token |
| `uncertain` | Внешний запрос мог быть принят; автоматического повтора нет, слот занят |
| `succeeded` | План опубликован; повторная доставка ничего не меняет |
| `stale` | Значимые входы изменились; нужен новый ключ и новая операция |
| `cancelled` | Отмена, недоступная цель/занятие или уже созданный план |
| `failed` | Известный отказ, некорректный ответ, истёкший cache или исчерпанные попытки |

Частичный UNIQUE допускает одну `queued/running/uncertain` операцию на занятие.
UNIQUE `(user_id, request_key)` возвращает существующую операцию при повторном
POST, включая конечное состояние. Чужой ключ и другой ключ занятого слота
отклоняются управляемой валидацией. Один ключ нельзя перенести на другое занятие.
UNIQUE плана по занятию дополнительно запрещает дублирование планов.

## Блокировки и актуальность

Общий порядок: `ScheduledTraining → TrainingPlan → TrainingPlanGeneration`.
При проверке доступности клиент/группа получает короткую shared-блокировку,
которая исключает архивирование между этой проверкой и commit публикации.
Ручной план проверяется под блокировкой занятия и никогда не перезаписывается.
Отмена занятия ставит постоянный маркер отмены активной генерации: последующее
возвращение занятия в `planned` не оживляет её. Старый worker после истечения
lease или смены token не может сохранить ответ либо опубликовать план.

SHA-256 рассчитывается из фактических сообщений LLM, ID владельца, точных
UTC-границ занятия и значимых параметров провайдера: provider, model, base URL,
max tokens, response format. Сообщения содержат цель, ограничения, выбранные
последние пять завершённых планов и их заметки, активную AI-память и текущие
доступные упражнения. Пересчитывается состав выборок, а не только timestamps.
Порядок записей стабилен; ключи JSON сортируются, порядок списков сохраняется.
Имя тренера, цвет занятия, технические timestamps и API key в hash не входят.

**Это не атомарный снимок всего контекста.** Общие User/advisory locks не добавлены.
Независимые изменения памяти, заметок, исторических занятий и каталога могут
попасть между SELECT разных частей контекста или между финальным hash и INSERT
плана. Fingerprint обнаруживает наблюдаемые изменения, но не закрывает эти окна.
Для строгой гарантии потребуется общая синхронизация соответствующих writers.

## Сбои и повторы

| Надёжно сохранённая фаза | Восстановление после истечения lease |
|---|---|
| Нет `request_started_at` | Можно вернуть в `queued` и вызвать LLM |
| Есть marker отправки, нет сохранённого ответа | `uncertain`, без повторного LLM |
| Есть сохранённый ответ | Возобновить публикацию без повторного LLM, вновь проверить контекст |
| `succeeded` | No-op; не менять план и timestamps |

Marker пишется перед внешним вызовом. Сбой между marker и фактической отправкой,
либо между получением ответа и его сохранением, трактуется консервативно как
`uncertain`. Exactly-once внешнего вызова без поддержки провайдера не обещается.
Закрытие `uncertain` требует явного `acknowledge_unknown=true`: новая операция
после закрытия может создать дополнительные расходы. Отмена работающей операции
запрещает публикацию, но не гарантирует прекращение уже отправленного HTTP-запроса.

Автоматический внешний retry разрешён только при подтверждённом безопасном отказе
(сейчас HTTP 429): максимум три попытки, backoff 30/120 секунд, учитывается
`Retry-After` до часа. Timeout, разрыв соединения и HTTP 5xx имеют неизвестный исход.
Известные постоянные отказы и невалидные ответы завершаются `failed`.
Сбой БД после сохранённого ответа позволяет повторить публикацию через 30 секунд.

| Параметр | Значение |
|---|---|
| HTTP timeout | OpenRouter 120 с, LM Studio 300 с; допустимо 1–300 с |
| Job timeout | 330 с |
| Lease | 360 с |
| Database queue `retry_after` | 420 с |
| Лимит доставок одной Job | 20; отдельно от лимита внешних попыток |
| Recovery | Каждую минуту через Laravel scheduler |

Recovery проверяет просроченные lease и восстанавливает доставку забытых `queued`
операций. Он работает независимо от worker, включая kill процесса, исчерпание
доставок и временную недоступность БД. Дубли Job возможны, но не дают второго
владельца lease. Без работающего scheduler автоматическое восстановление и
очистка по сроку хранения не гарантируются.

## API и данные

- `POST /scheduled-trainings/{id}/training-plan-generations`: UUID `request_key`,
  JSON 202 с `generation`; Inertia получает redirect на страницу занятия.
- `GET /training-plan-generations/{id}`: минимальный статус только владельцу.
- `POST /training-plan-generations/{id}/cancel`: отмена; для `uncertain` обязательно
  подтверждение неизвестного результата. Чужая операция возвращает 404.
- Старый `POST /scheduled-trainings/{id}/generate-training-plan`: HTTP 410 без LLM.

Ни status API, ни Job не раскрывают контекст, cache, run token или lease.
В обычных AI-логах этого pipeline сохраняются только metadata; previews prompt
и ответа отсутствуют, сообщения ошибок не содержат пользовательский контекст.
Зашифрованный ответ удаляется при завершении либо по истечении 24 часов.
Метаданные конечных операций хранятся 90 дней, failed_jobs этого типа — 30 дней.
Неразрешённые `uncertain` по возрасту не удаляются. После очистки метаданных
идемпотентность старого ключа не гарантируется. APP_KEY нужно сохранять:
нечитаемый cache завершится ошибкой без нового внешнего вызова.

## Запуск и обновление

```sh
php artisan migrate --no-interaction
php artisan queue:work training-plan-generations --queue=training-plan-generations --timeout=330 --tries=20
```

В другом процессе для локальной разработки:

```sh
php artisan schedule:work
```

На сервере нужны управляемый worker и cron с `php artisan schedule:run` каждую
минуту. После обновления кода/config перезапустить долгоживущие workers через
`php artisan queue:restart`. Применить обе миграции до их запуска. Рабочая БД
и выделенная очередь должны использовать одно соединение PostgreSQL; проверка
транзакционности отклоняет несовместимую конфигурацию до создания новой операции.

Резервы из этапа 1 без fingerprint получают `stale` и требуют явного нового
запуска. История и существующие планы не мигрируются и не исправляются.
Квоты публичного запуска и поддержка идемпотентного ключа у провайдера остаются
отдельными задачами; текущий лимит ограничивает попытки одной операции.
