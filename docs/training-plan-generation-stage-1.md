TrainingPlanGeneration: этап 1

Это исторический отчёт на момент завершения этапа 1. Этап 2 реализован;
актуальные правила, запуск worker и ограничения описаны в
[отчёте этапа 2](training-plan-generation-stage-2.md).
Указания ниже о Job-заготовке и запрете запуска очереди больше не действуют.

Реализованы хранение операции, атомарное резервирование и отдельный POST.
LLM, fingerprint, публикация результата, retry/recovery и UI не реализованы:
это согласованный этап 2. Существующий синхронный generate-training-plan
остаётся прежним до переключения на этапе 2 и пока сохраняет риски REVIEW-003/006.

POST /scheduled-trainings/{scheduled_training}/training-plan-generations
принимает request_key (UUID), требует существующую авторизацию владельца и
возвращает HTTP 202 с generation: id, scheduled_training_id, request_key,
status и created_at. Другие поля входа не используются. Новая операция допустима
для planned без плана и с активным клиентом/группой того же владельца.

Идемпотентность

- UNIQUE(user_id, request_key) связывает принятый ключ с одной операцией.
- Повтор её ключа возвращает ту же запись без UPDATE и повторной Job, даже если
  занятие позднее отменено или операция уже получила конечный статус.
- Повтор ключа для другого занятия того же пользователя — validation error 422.
  Разные пользователи могут независимо использовать одинаковый ключ.
- Другой ключ при активной операции занятия получает validation error 422.
  Он не принимается как скрытый алиас: иначе повтор этого ключа после завершения
  мог бы создать другую операцию. После конечного состояния допустим новый ключ.

Ограничения PostgreSQL

Статусы: queued, running, uncertain, succeeded, stale, cancelled, failed.
retry_wait объединён с queued + next_attempt_at. Активные состояния — queued,
running и uncertain; частичный UNIQUE по scheduled_training_id запрещает второй
активный резерв. CHECK ограничивает статусы, неотрицательные attempt_count и
наличие run_token/lease/положительной попытки у running.

scheduled_training_id допускает SET NULL при удалении занятия. Запись операции
сохраняется; CHECK не требует непустой ссылки и не воспроизводит конфликт
nullOnDelete с ограничениями из REVIEW-001. Удаление аккаунта сохраняет прежнюю
каскадную семантику. История самих планов и существующие DELETE не переопределены.

Транзакция резервирования

ReserveTrainingPlanGeneration использует connection модели занятия. Выделенная
queue connection training-plan-generations — database, на pgsql, table jobs.
Проверяется не только имя БД, но идентичность объекта Connection: другое
соединение к той же БД не делает два INSERT атомарными и отклоняется до записи.

Порядок блокировок: ScheduledTraining → существующий TrainingPlan → Generation.
Состояние и наличие плана читаются заново после блокировки. Внутри этой же
транзакции создаётся queued Generation и через Bus::dispatch вставляется Job.
Job явно использует beforeCommit(), поэтому её INSERT не переносится в callback
после commit, даже если queue after_commit включат. Драйвер database использует
тот же объект соединения; никакого sync driver, Queue::fake или Redis в этом пути нет.

INSERT ON CONFLICT DO NOTHING закрывает также гонку одного request_key между
двумя разными занятиями: проигравший читает принятую запись и получает управляемую
ошибку привязки ключа. Блокировка занятия сериализует конкуренцию одного занятия;
partial UNIQUE страхует ограничение на уровне БД. SQL-транзакции допускают до
трёх стандартных Laravel retries для deadlock/serialization conflicts.

Job-заготовка

GenerateTrainingPlanJob хранит только generation UUID. handle содержит защитный
отказ с объяснением отсутствия этапа 2 и не меняет Generation/не обращается к AI.
Он нужен для настоящего сериализованного jobs payload и проверки транзакционности,
а не является реализованным worker.

Не запускать выделенную очередь training-plan-generations до этапа 2. Обычный
worker очереди default её не потребляет. При ошибочном запуске заготовка завершится
ошибкой, Job может перейти в failed_jobs, а queued резерв останется: это требует
восстановления после реализации этапа 2. Автоматического recovery сейчас нет.

Данные и хранение

В Generation сохраняются UUID/ключ, владелец и ссылка на занятие, статус,
счётчик попыток, next_attempt_at, run_token/lease и timestamps. Полного контекста,
prompt, персональных заметок, ответа LLM и API keys нет ни в новой таблице,
ни в Job. Response не раскрывает user_id, run_token или lease. Новых обычных
логов пользовательского контекста не добавлено; старый AI logger не менялся.

Политика для внедрения cleanup на этапе 2: конечные метаданные — 90 дней после
завершения; failed_jobs этого типа — 30 дней. queued/running/uncertain нельзя
удалять по возрасту без выяснения состояния: uncertain должен удерживать слот.
Идемпотентность должна сохраняться не меньше срока метаданных; после его истечения
повтор старого ключа больше не гарантируется. Сейчас автоматическое удаление не
включено, записи сохраняются до следующего этапа.

Обязательные решения этапа 2

- run_token и lease должны проверяться при claim/checkpoint/публикации; наличие
  колонок само по себе не защищает позднего worker. Сейчас running не создаётся
  публичным POST и автоматических внешних попыток нет.
- Предварительные границы: HTTP 120/300 секунд; Job 150/330; lease 360;
  retry_after 420. Job timeout < lease < retry_after позволяет повторной доставке
  увидеть уже истёкший lease вместо молчаливого ACK ещё running операции.
  Эти параметры применяются и проверяются перед включением обработчика; текущие
  queue retry_after=90 не предназначены для LLM.
- Дубликат при ещё действующем lease должен быть отложен до проверки владельца
  или покрыт обязательным recovery. Периодический recovery нужен и при kill -9 /
  отсутствии новой доставки. Сохранённый ответ продолжается без LLM; неизвестный
  исход внешнего запроса становится uncertain, без автоматического повторного POST.
- Fingerprint будет проверяться перед публикацией по фактически использованным
  входам; общие User/catalog advisory writer-locks не вводятся по согласованию.
  Несколько SELECT могут собрать смешанный контекст. Профиль, память, заметки и
  каталог могут измениться между повторным чтением/hash и INSERT плана; новые
  строки меняют членство наборов. Одна блокировка ScheduledTraining эти окна не
  закрывает. Нельзя заявлять полную атомарность контекста.
- Состояние занятия, наличие ручного плана и активность цели должны проверяться
  отдельно при публикации. Для архивирования между проверкой и commit потребуется
  короткая блокировка строки цели; общий writer-lock всех моделей этим не заменяется.
- Отмена/архивирование после резервирования, queued orphan после удаления занятия,
  работа старого синхронного пути, квоты и status UI закрываются на этапе 2.

Проверки

41 новый PostgreSQL-сценарий проверяет POST, ключи, права, актуальные проверки,
CHECK/UNIQUE/FK и защитную Job. Полный Pest: 302 сценария, 298 passed, 4 skipped,
2067 assertions. PHPStan/Larastan level 7 — 0 ошибок; Pint 12 PHP-файлов и
git diff --check, включая новые файлы, пройдены.

Транзакционная suite tests/Integration использует DatabaseMigrations вместо
обёртки RefreshDatabase, чтобы commit был настоящим. Перед миграциями она требует
PostgreSQL и database testing (либо testing_test_N); рабочая БД не сбрасывается.
phpunit.xml включает эту suite в обычный полный запуск Pest.

Подтверждено отдельным соединением: обе записи невидимы до commit, обе видимы
после него; rollback и ошибка enqueue после INSERT удаляют обе. Исключение в
RequestHandled моделирует сбой после commit до возврата HTTP-ответа: Job остаётся,
повтор запроса возвращает тот же UUID без второго INSERT.

Три гонки запускают два отдельных PHP-процесса: одинаковый ключ/занятие,
разные ключи/одно занятие, один ключ/разные занятия. pg_stat_activity подтверждает
ожидание обеими транзакциями lock на ScheduledTraining перед снятием барьера;
во всех случаях сохраняются ровно одна Generation и одна Job.

Миграция проверена на чистой testing при каждом транзакционном тесте, включая
rollback миграций, и применена в локальной trainer_workspace (APP_ENV=local).
Изменение локальной схемы добавочное, существующие бизнес-данные не изменяются.
Этап 2 не начат; коммит не создавался.
